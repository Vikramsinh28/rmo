Executive summary

  • The pipeline works end to end. The deployed AI service finds people in video, tracks them, reads body posture and facial signals, and produces a live status (Normal / Monitoring / Elevated / High / Insufficient evidence) with written evidence for each person.
  • It is cautious by design. Across 5 normal-behaviour clips it raised no false alerts. It raised an alert on 1 of 5 impairment clips: a staged 1916 film showing exaggerated drunk behaviour, where it reached High, with the first alert 50 seconds into the clip.
  • It did not alert on any of the 3 real-world impairment clips (police dash-cam and body-cam). On 2 of them it showed the early-warning Monitoring status. The main reasons were camera conditions: face or lower body out of view, night footage, and subjects mostly standing still or seated.
  • Results are reproducible. A second, independent run on a different machine gave the same highest status on 9 of 10 clips. The tenth differed only between Insufficient evidence and Normal.
  • Software checks pass: 74 of 74 AI-service unit tests, 41 of 41 platform API tests (safety events, review, audit, access control, live alerts, licensing) and a clean type-check.
  • Recommendation: the system is ready for a supervised pilot with data collection in 1–2 lobbies. It is not ready to drive any automatic action. Alerts must stay a prompt for a human check (e.g. breath test).
Important: the system reports visual indicators such as unsteady posture, sway or eye closure. It does not diagnose intoxication. Illness, fatigue, injury or disability can produce the same indicators. Every alert goes to a trained reviewer.

What was tested and how

  • Footage: 10 clips (11.5 minutes, about 3,450 frames) from Wikimedia Commons, all public domain or openly licensed. There are 5 impairment clips (2 staged films, 3 real police recordings) and 5 normal clips (people walking or standing).
  • Method: each clip was replayed frame by frame at 5 frames per second through the same AI service container that runs in the application, using the video's own timing, the same way a live lobby call is processed.
  • Measured: the highest status reached, how long each status was shown, when the first alert appeared, image quality, how often the face and full body were visible, and which evidence the system reported.
  • Pass criteria: an impairment clip passes if it reaches Elevated or High. A normal clip passes if it never reaches Elevated or High. Monitoring is an early-warning state and does not raise an alert.

How the system decides

Six signal groups are scored per person over a rolling 10-second window: gait, sway, posture, head movement, eyes and arm coordination. An Elevated alert needs a combined score of at least 0.5, with at least two groups independently strong, sustained for 8 seconds. High needs at least 0.7 sustained for 10 seconds. The system abstains (Insufficient evidence) when the view is too poor or too short. These rules deliberately trade sensitivity for fewer false accusations.

Limitations of this test

  • Small sample. 10 clips is enough to show the system works and to spot its failure modes. It is not enough to quote accuracy percentages with confidence.
  • The footage is not lobby footage. Old films, dash-cams and body-cams have different angles, lighting and motion from a fixed lobby camera. Real lobby performance is still unknown.
  • No confirmed ground truth. The real clips show suspected impaired drivers. There are no breath-test results for them.
  • Staged films exaggerate behaviour. The Chaplin detection shows the logic works on clear cases, not that subtle impairment will be caught.
  • Known weakness: a person walking slowly straight away from the camera can be partly read as sway, as in the walking-sands clip, which reached Monitoring but no alert.
  • Processing speed: during this run the container took 101–236 ms per frame on CPU inside Docker (a separate native run took 61–104 ms). That supports roughly one live call at 5 frames per second. Several simultaneous calls will need a GPU or a dedicated server.

Recommendations and next steps

  1. Supervised pilot in 1–2 lobbies with a fixed camera placed to see the full body and the face, with good lighting. The test shows camera placement matters more than anything else.
  2. Collect ground truth through the built-in review form. Every alert already records the reviewer's outcome and breath-test result, so the pilot builds a labelled dataset automatically.
  3. Calibrate thresholds on pilot data. For example, strong eye-closure plus head-instability cases (like the DUI booking clip) may justify a faster alert. That change should come from data, not from these 10 clips.
  4. Before the pilot: sign off the privacy notice and consent wording, and set a data-retention period for snapshots and events.
  5. Plan hardware for scale: a GPU server before rolling out beyond a few simultaneous calls.
  6. Keep a human in the loop. An alert is a prompt to check, never an automatic decision about duty.
